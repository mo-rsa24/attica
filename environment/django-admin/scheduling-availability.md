# 🗺️ What makes a provider bookable

An artist in the catalogue is not a bookable artist. Five separate rows have to line up before the
scheduler will return them, and when one is missing the search returns an empty list with no error,
which reads exactly like "this artist is busy".

What to click to create them is
[../../runbook/preparing-the-data/preparing-artist-availability.md](../../runbook/preparing-the-data/preparing-artist-availability.md).

## The five rows, in order

Navigation: 📋 [TOC](#table-of-contents) | [Next](#the-fields-that-silently-block-a-request) ➡️

All five live in `backend/main/scheduling/models.py`. Each depends on the one above it.

| # | The row | Without it | Where it is edited |
|---|---|---|---|
| 1 | `MarketplaceResource` linked to the artist | the artist is not a scheduling entity at all; nothing else can be created | `Scheduling > Marketplace resources` |
| 2 | `ResourcePolicy` for that resource | requests can be created and then rejected on rules nobody set | `Scheduling > Resource policies` |
| 3 | at least one active `AvailabilityRule` | there is nothing to generate slots from | `Scheduling > Availability rules` |
| 4 | materialized `AvailabilitySlot` rows covering the searched range | search returns nothing, however correct the rule looks | generated by a command, listed under `Scheduling > Availability slots` |
| 5 | no blackout `AvailabilityException` overlapping the range | the range is excluded even though slots exist | `Scheduling > Availability exceptions` |

**Row 4 is the one that is always missing.** A rule is a recurrence ("every Saturday 10:00 to
18:00"). A slot is one concrete window written out as a database row. The search reads slots, never
rules, so a correct rule with no slots behind it is invisible. Why the system is built in two
layers is in [../../context/world/availability.md](../../context/world/availability.md).

**Changing a rule does not update the slots already generated from it.** The old rows stay exactly
as they were, so the screen and the search disagree until the range is rematerialized.

## The fields that silently block a request

Navigation: ⬅️ [The five rows](#the-five-rows-in-order) | 📋 [TOC](#table-of-contents) | [Next](#weekdays-are-integers-monday-is-zero) ➡️

Two fields on `ResourcePolicy` reject a booking request for reasons that look like a bug in the
booking form.

**`min_notice_hours` defaults to 24** (`models.py:97`), so a same-day booking fails on a policy
nobody configured. The request is refused with `PolicyViolationError` at `services.py:153`, which
surfaces as a rejection rather than as an empty search, so the slot looks available right up until
the request is submitted.

**`require_message_for_request`** defaults to off, and when enabled rejects any request submitted
without message text (`services.py:449`).

A slot also has to pass its own two conditions to be offered: `is_bookable` checked, and
`capacity_reserved` below `capacity_total`.

## Weekdays are integers, Monday is zero

Navigation: ⬅️ [The fields](#the-fields-that-silently-block-a-request) | 📋 [TOC](#table-of-contents) | [Next](#who-is-supposed-to-manage-this) ➡️

`AvailabilityRule.weekdays` is a list of integers, `0` for Monday through `6` for Sunday. Every day
of the week is `[0, 1, 2, 3, 4, 5, 6]`.

This is Python's convention, not the one the browser uses. JavaScript's `getDay()` returns `0` for
**Sunday**, so a weekday index copied from frontend code lands one day out and the artist is
available on the wrong days.

## Who is supposed to manage this

Navigation: ⬅️ [Weekdays](#weekdays-are-integers-monday-is-zero) | 📋 [TOC](#table-of-contents)

**Two surfaces exist and they are not equivalent.** `/provider-availability` in the app is the
intended one: the logged-in artist manages their own resource, and the API checks ownership before
saving (`backend/main/scheduling/permissions.py`). The admin is the operator's fallback, for
preparing demo and test data across accounts you do not have passwords for.

**A blackout is deleted, not deactivated.** `AvailabilityException` has no active flag
(`models.py:178`), so making a provider bookable again means removing the row. There is no way to
keep it for the record.
