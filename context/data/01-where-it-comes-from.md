# 🌍 Where the data comes from

Attica has no upstream data source. **Every row in it was typed by a person into a screen**, or
generated by a seed script for demonstration. There is no ingestion, no external feed, no
extract-transform-load step, and no historical archive.

That is unusual enough to be worth stating first, because it inverts the usual worry. Nothing here
is stale because a source changed. Everything here is exactly as reliable as the person who typed
it, which is a different problem.

## The journey

Navigation: 📋 [TOC](#table-of-contents) | [Next](#what-happens-before-we-see-it) ➡️

**An organizer's data arrives through a wizard, in pieces, over days.** ✅

They open the event creation flow and work through it a screen at a time. Each step saves to an
[event draft](../world/event-draft.md#what-an-event-draft-is), into a single JSON blob rather than
into typed columns. At publish, `_upsert_event_from_draft` reads that blob and writes a real
[event](../world/event.md#what-an-event-is) row with proper columns.

**So one fact about an event exists in two shapes at two different times.** ✅

Loosely typed inside `EventDraft.data` while being edited, and strictly typed in `events_event`
after publish. A guest count is a JSON value first and an integer column second, and the conversion
happens at exactly one moment.

**A provider's data arrives through profile forms and availability rules.** 🔍

A venue, artist or vendor fills in their profile, then publishes availability as recurring rules.
Those rules become bookable slots only when a management command materializes them; see
[Availability](../world/availability.md#what-availability-is).

**Uploaded files land on local disk and the database keeps a pointer.** ✅

Event draft assets go to
`media/event_draft_assets/organizer_<id>/draft_<id>/<asset_type>/<uuid>.<ext>`. The row holds the
path, the declared mime type and a name; the bytes are on the filesystem.

## What happens before we see it

Navigation: ⬅️ [The journey](#the-journey) | 📋 [TOC](#table-of-contents) | [Next](#the-one-external-source) ➡️

**Nothing. That is the honest answer, and it matters.** ✅

There is no cleaning step, no deduplication, no validation pass beyond what a form and a model
field enforce. What a user typed is what is in the database.

**Which makes the weak field types the whole data quality story.** ✅

`Artist.genres` is free text, so two Amapiano artists may not match each other.
`EventDraft.current_step` has no choices, so a typo is a legal value. `Event.venue` is free text
beside a `location` foreign key. Every one of those is a place where the same real-world fact can
be recorded two ways and never reconciled, because nothing downstream reconciles anything.

**Two fields are computed rather than entered.** ✅

`Vendor.rating` is averaged from that vendor's service ratings by `update_rating()`, and
`AvailabilitySlot.capacity_remaining` is derived from total minus reserved. Everything else is
entered.

## The one external source

Navigation: ⬅️ [What happens before we see it](#what-happens-before-we-see-it) | 📋 [TOC](#table-of-contents) | [Next](#what-is-real-and-what-is-seeded) ➡️

**Geocoding and map tiles come from OpenStreetMap, straight from the browser.** ✍️

The location step calls `nominatim.openstreetmap.org` and fetches OSM tiles directly. The Attica
backend never sees those requests, so nothing about them appears in server logs and nothing is
cached. A latitude and longitude stored on a venue came from that service at the moment someone
picked a point on a map.

## What is real and what is seeded

Navigation: ⬅️ [The one external source](#the-one-external-source) | 📋 [TOC](#table-of-contents) | [Next](#where-this-came-from) ➡️

**Much of the development database is demonstration data written by management commands.** ✅

`seed_marketplace`, `seed_booking_workflow`, `seed_booking_summary_demo`, `seed_sa_artists`,
`seed_sa_locations` and `load_bookings` all exist. The artists and venues in the database are
recognisable South African names and places loaded by those commands.

**Seeded rows are not marked as seeded.** 🔍

Nothing in the schema distinguishes a row a real user created from one a seed command wrote. So
"has anyone actually used this" cannot be answered by querying, which is why it sits on the
[index's Still open list](../00-INDEX.md#still-open).

**There is one deterministic fixture for automated testing.** ✅

`seed_e2e` creates the organizer `e2e-organizer`, used by the browser test suite.
